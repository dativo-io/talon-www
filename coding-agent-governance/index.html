Session-first view

Move from request logs to a run you can explain.

The primary question is not “what HTTP requests happened?” It is “what happened in this session, what did it cost, which providers and subagents were involved, what was denied, and why did it end?” Current Talon supports useful pieces of that view for asserted sessions.

Attribution

Neutral orchestration contract

The role names belong to your workflow, not Talon.

Planner, generator, reviewer and executor are examples only. Talon does not spawn or authenticate them. Generic X-Talon-* metadata and supported client mappings provide attribution so the session history can be explained.

Session cost control

Stop a new request when an asserted session crosses its configured soft cap.

max_session_cost is caller-scoped. A new request is denied once accumulated spend plus the pre-request estimate exceeds the limit across supported provider routes. The denial uses the provider’s native error shape and carries structured signed evidence.

Boundary: in-flight and concurrent requests can overshoot; strict atomic reservation is not claimed.

Cost pillarBudget semantics
policy_overrides:

Honest boundaries

What session visibility does not mean.

No fake grouping

Synthetic request-level IDs are evidence correlation, not invented multi-request sessions.

No local action visibility

Files edited, commands run and tools executed locally remain invisible when they never cross Talon.

No identity attestation

Client-asserted agent and subagent labels explain traffic; they are not authenticated identities.
