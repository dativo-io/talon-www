The operating problem

Independent AI apps create independent policy drift.

A support bot, coding agent and internal assistant should not each invent their own answer to sensitive data, model access, budget and egress. Talon centralizes enforcement on paths it can actually intercept.

Shared intent

Use common runtime defaults for provider/model access, cost, PII, tools and regional posture.

Explicit use-case needs

Keep differences visible instead of hiding them in application code or ad-hoc gateway keys.

One decision history

Record policy reasons in the same evidence model used for cost, sessions, routing and incident review.

Current implementation

Configuration is not fully normalized yet—and the website does not pretend otherwise.

Current Talon capabilities are split across agent.talon.yaml, talon.config.yaml, gateway callers and provider settings. The product direction is simpler: one AI use case should have one operational identity and one effective policy. The site does not claim the final baseline-plus-override contract is fully shipped.

Tool boundary

Govern only actions Talon can actually intercept.

Tool schemas visible in LLM requests can be filtered or blocked. MCP calls routed through Talon can be governed. Local shell commands, file edits, browser actions and direct APIs that bypass Talon are outside the control plane.

Evidence under policy

Prove how the control plane behaved.

Evidence is not the entire product category. It is the proof layer under operation: the reason a request was allowed, denied, redacted, routed, failed over or stopped by budget can be inspected and verified later.

Decision

Allow, deny, redact, filter, route or fail-closed outcome with reasons.

Context

Caller/agent attribution, model/provider, session, cost, PII and destination facts where present.

Integrity

HMAC signatures make stored records tamper-evident and verifiable.

Start small
