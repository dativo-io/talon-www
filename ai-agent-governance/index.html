Category and implementation

AI use case is the stable product object. Agent is today’s OSS implementation object.

Publicly, Talon governs AI use cases independent of runtime or provider. Today, configuration, authentication, evidence and attribution still use the Talon agent object. That implementation detail may evolve without changing the company policy/use-case contract.

One real use case first

Start with the support bot, coding workflow or product feature where a company rule must prevent or authorize a real outcome.

Keep the orchestrator

Talon does not decide tasks, spawn subagents or replace LangGraph, Claude Code, Codex or your application logic.

Reuse the company control model

Keep policy semantics stable while the technical enforcement point changes across model gateways, MCP, runtime hooks or other supported boundaries.

Identity contract

The application presents an agent key, not a free-form identity claim.

agent.key.secret_name points to one encrypted vault secret. Talon resolves the presented key to the agent and tenant, rejects unknown keys, and prevents the request from acting as a different agent. The admin key remains a separate authority.

Authentication referenceConfigure an agent
agent:
  name: customer-support
  tenant_id: acme
  key:
    secret_name: customer-support-talon-key

# bearer key → customer-support → acme
# body/header cannot substitute another identity

Effective policy

Use one policy snapshot across the complete provider path.

The organization baseline and agent override resolve into the same effective policy used by the primary route, every fallback candidate, budget reporting and evidence. Organization PII, provider/model, tier and egress boundaries cannot be weakened by an agent.

Action boundary

Agentic does not mean universally controllable.

Talon can govern provider-bound traffic, tool schemas visible to the gateway and MCP/tool calls routed through its interception path. Current interception can deny disallowed calls before upstream execution; the active Action Gateway direction adds exact-operation authorization and durable approval. Local shell commands, file edits, browser actions and direct APIs that bypass Talon remain outside the control plane.

Fleet operations

One Talon process can serve a discovered fleet of AI use cases.

agents_dir recursively discovers agent files, each use case resolves its own compiled policy/runtime bundle, and safe periodic reload keeps the last-known-good generation active when a new edit is invalid. Runtime identity remains bound to the configured use case rather than caller-supplied metadata.

Adopt incrementally

Put one real AI use case under one company rule.

Use the current agent file/key mechanism to route the path Talon can govern, trigger a meaningful policy or action decision, verify the evidence, and only then add use case #2 to test whether the shared control model actually reduces governance duplication.
