The real governance sequence

Do more than declare “EU preferred.”

A useful control must connect request sensitivity, destination policy, actual execution, and reviewable evidence.

Two provider-control paths

Chosen destination and policy-selected destination are different problems.

Gateway proxy: the provider is encoded in the route the client called. Talon can allow or deny that provider-bound request. It does not silently turn an OpenAI proxy request into an Ollama request.

Policy-aware runner: Talon owns candidate selection. It can classify the request, reject OpenAI/US before dispatch, select Ollama/LOCAL, and record both outcomes.

Same sensitive data, different policy outcome

Block it — or process it under a stricter execution constraint.

In the governed-session proof, an IBAN sent through an enforcing gateway caller is blocked before any provider call. The same type of confidential data sent through the policy-aware runner is allowed to be processed, but only after the US candidate is rejected and a LOCAL model is selected.

The difference is explicit policy context, not a hidden exception.

EU and local posture

Enforce before execution, then review observed behavior.

EU strict

Reject non-EU/LOCAL candidates where Talon controls routing and fail closed when no allowed candidate remains.

Air-gap / local-only

Use explicit LOCAL/EU providers and deny-by-default egress posture for private or disconnected deployments.

Runtime consistency

Compare declared residency with signed observed destinations and surface non-EU flows that require stricter policy or documented transfer mechanisms.

The receipt

Rejected candidates are part of the evidence.

A successful local response is not enough. Talon records why a candidate was rejected, which provider and model were selected, the session and correlation context, and the signed runtime facts needed for later review.
