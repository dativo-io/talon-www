Concrete support workflow

Useful drafts should survive a blocked financial action.

The existing n8n customer-support resolution demo starts with a fictional duplicate-charge ticket, account context and refund policy. A preferred local model route fails; Talon skips a forbidden provider candidate and allows an approved OpenAI fallback on the redacted request. The draft can be completed even though the subsequent request exposing issue_refund is denied before upstream model dispatch.

Data handling

The synthetic input contains an email and IBAN. The governed model path records redaction decisions; it is not a blanket DLP guarantee for systems outside Talon.

Provider reliability

Fallback candidates are checked against the use-case's provider and data policy. A model-provider failure is not proof that the complete support workflow has failed.

Preventive tool restriction

The disallowed issue_refund tool schema cannot pass this governed provider request. This does not assert control of every directly invoked payment API.

Where approval actually happens

The n8n operator gate is not a Talon-initiated refund.

After Talon denies the disallowed model request, n8n enters a literal human approval state. The workflow waits until a demo operator approves or rejects the exact synthetic EUR 249 finance request. On approval it creates a finance-handoff artifact; on rejection no handoff is created. Neither branch issues an actual refund.

That human gate belongs to the n8n demo workflow. It is not the separately shipped HTTP Action Gateway's authorization/dispatch lifecycle and should not be presented as Talon automatically approving payment execution.

What a buyer can inspect

Two perspectives on the same synthetic workflow

Support lead

The reply draft remains available. The application explicitly records that refund processing requires a separate human decision.

Platform engineer

The configured customer-support identity, approved provider fallback, denial, estimated cost and relevant session records can be inspected.

Security reviewer

Verify signed Talon decisions for routed traffic and separately signed demo-operator receipts. No claim extends to direct calls bypassing the controlled path.

The support inputs and financial handoff are synthetic. A separate Zendesk-adapter scenario exists, but installation and UI observations in a real Zendesk account require additional operator confirmation.
